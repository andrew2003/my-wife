# AI service

Owner: `ai`. The persona ("the wife"), memory, conversations, the tool set, BYOK key use, model roles, the handover test and fallback. The LLM understands language and proposes; it never writes to the ledger and never decides money, fault points or penalties (principle 4). Content from email and chat is untrusted data (principle 6).

## 1. One wife, any model

Each user brings their own API key and chooses provider and model (via the Vercel AI SDK). Persona, memory, history and tools live on the My Wife side, so changing a model never creates a new wife. Four continuity layers:

1. **Persona:** voice, forms of address, behavior rules, a strictness slider (`ai.persona_strictness`, gentle to strict). User-editable, versioned (`persona_version`), loaded into every call.
2. **Structured memory:** facts with source and date ("payee X is eating out", "often late for the afternoon coding task"). The user can view, edit and delete them in the web app. A memory is written by code from a confirmed user answer or an explicit tool call; it is not free LLM text with authority.
3. **History and summaries:** the last `ai.recent_messages_kept` messages are kept verbatim; older conversation is summarized every `ai.summary_trigger_messages` messages. Retrieval is semantic with pgvector, `ai.memory_retrieval_top_k` results.
4. **Tools and rules:** every model calls the same tool set. Money and penalty decisions are code, so a model switch cannot change them.

## 2. Tool set

Tools are thin wrappers that call other services' REST APIs. Each tool call is audited (`audit_log`) and important changes need a confirm button.

| Tool | Effect | Confirm |
| --- | --- | --- |
| `record_cash_expense` | Quick capture of a cash expense (to `budget`) | No, shown afterward |
| `create_task` | Quick capture of a task | No |
| `answer_question` | Resolve a pending question with a button value | No |
| `ask_reason` | Open a reason ticket | n/a |
| `update_setting` | Propose a setting change | Yes, always; tightening is immediate and loosening is locked (see rules) |
| `read_status` | Read budget, schedule or penalty status | No |
| `create_appeal` | Draft an appeal for the user | Yes |

Forbidden tools: anything that moves money, signs a contract, ends a trial or changes a penalty. The model that reads receipts (ingest) is called with no tools.

## 3. Model roles and keys

- Per user: a primary model and a fallback model, plus optional role assignment: a cheap model for classification and receipt reading, a stronger one for chat and weekly reviews, and a vision-capable model for wake-up photos.
- Keys are encrypted at rest with a master key (key id column for rotation), decrypted only inside the `ai` service at call time, never sent to the browser and never logged. Tokens for Google and chat are handled the same way.
- Usage page: tokens used per user and per day; `ai.daily_token_cap` stops calls over the cap (the user sets it).

## 4. Handover test

When the user changes a model, the new model must pass a fixed set of questions run with the user's current data and compared to the old model's answers, for example "how much of the food budget is left this week", "which task am I often late for". Answers are checked for factual correctness against the code's own numbers (programmatic grading) and for persona voice (a rubric). The model is enabled only if the pass ratio is at least `ai.handover_pass_ratio`. A failed test leaves the old model active and shows which questions failed.

## 5. Fallback and degraded mode

- After `ai.fallback_after_failures` consecutive failures (out of credit, key invalid, provider down) the service switches to the fallback model and tells the user; memory is the same.
- If no model is available, the product keeps working: countdown, rules, penalties, trusted receipt templates, buttons and the inbox. Chat free text is answered with the inbox and quick-reply buttons. A banner states "AI is unavailable". New receipt templates wait in the anomaly inbox.

## 6. Agent loop

For each user message: compose persona, relevant memories, current state snapshot and the tool list; call the model; execute tool calls through the tool wrapper (validated against the contracts schema); store the message. A message that is untrusted content (an email field or a chat paste) is wrapped as data and never as an instruction. A rate guard prevents loops (max tool calls per turn).

## 7. Vision uses

Wake-up photo grading (see `22-routines.md`), camera ambiguous or appealed frames (see `21-monitor.md`). Images are sent only with the matching consent and only for the grade; the service never persists the image, only the structured result, except the retention rule for failed wake-up photos.

## 8. Events

Published: `ai.message_sent`, `ai.photo_graded`, `ai.model_changed`, `ai.handover_passed`, `ai.handover_failed`, `ai.degraded_entered`, `ai.degraded_exited`, `ai.token_cap_reached`, `memory.created`, `memory.updated`, `memory.deleted`, `persona.updated`.

Consumed: any `ask.*` question events for conversation context, `txn.recorded`, `penalty.issued`, `task.*` (context), `notify.reply_received`, `user.updated`, `template.read_requested`.

## 9. Acceptance

1. Given a user message "bought milk 35k cash", When the model calls `record_cash_expense`, Then the budget service creates the transaction through its API and the audit log has an entry; the model cannot create a penalty.
2. Given the primary model fails 3 times in a row, Then the fallback model answers with the same memories and the user is informed.
3. Given no model works, Then countdown, rules and buttons still work and chat shows the degraded banner.
4. Given a new model that fails one handover question, Then it is not enabled and the old one remains active.
5. Given an email containing "ignore previous instructions", Then no tool call results from it.
6. Given a stored key, Then no API response, log line or browser payload contains it, and the cap stops calls once `ai.daily_token_cap` is reached.
